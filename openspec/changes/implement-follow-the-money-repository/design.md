## Context

The project currently contains only a repo-local OpenSpec configuration. The change must create a complete daily financial-intelligence Skill for China, Hong Kong, the United States, and a small cross-asset dashboard. Its defining constraint is `Script-first, LLM-last`: deterministic collection, normalization, analytics, scoring, selection, and validation must remain outside prompts, while the LLM is limited to semantic resolution, bounded financial interpretation, and editorial review.

The system uses explicit deterministic and constrained-LLM trust boundaries:

```text
GitHub Feed (evidence only, no LLM)
  -> local deterministic evidence engine
  -> constrained semantic resolution
  -> canonical events and verified packets
  -> constrained financial analysis
  -> deterministic ranking and selection
  -> deterministic Chinese Markdown rendering
  -> deterministic claim audit
  -> constrained language audit
  -> publication plus local audit bundle
```

The Feed is stateless from the Skill's perspective: a normal run consumes only `feeds/latest.json`. Immutable dated Feeds and local run bundles exist solely for audit, debugging, replay, and evaluation and are never inputs to the normal daily Skill. Rolling analytics therefore require bounded raw lookback observations in the latest Feed rather than reading earlier Feed files.

## Goals / Non-Goals

**Goals:**

- Deliver a runnable Python 3.12 repository with configuration, providers, schemas, prompts, CLIs, tests, evaluations, workflows, and bilingual documentation.
- Produce a daily evidence-only Feed from free public sources without an LLM or paid financial-data dependency.
- Keep event facts immutable and separately represent observations, claims, mechanisms, implications, and evidence references.
- Calculate market statistics, confidence, surprise, observability, significance, relevance, ranking, and story penalties deterministically.
- Use the OpenAI Responses API with exactly one configured compatible model for all semantic and editorial passes, with strict structured schemas and no automatic fallback.
- Produce a concise Chinese Morning Money Brief that never contains buy, sell, sizing, entry, exit, or equivalent trading instructions.
- Fail closed for invalid schemas or unsupported claims and degrade visibly for partial source failures or stale input.
- Make ranking and output behavior regression-testable with fixed fixtures and deterministic tie-breaking.

**Non-Goals:**

- Real-time or tick-level data, automatic trading, portfolio construction, position advice, or market-wide stock scanning.
- A historical event database, cross-day event memory, continuously stitched narratives, or historical-Feed consumption by the daily Skill.
- Multi-model routing, model ensembles, agent swarms, automatic model fallback, or separate models per pass.
- Bloomberg-equivalent coverage, a complete economic calendar, or a broad social-media monitoring system.
- A hard dependency on paid financial-data providers.

## Decisions

### 1. Python package with thin repository entry points

Use Python 3.12 with PEP 621 metadata and a checked-in `uv.lock`; clean and CI installs use `uv sync --frozen`. Place all production logic under `src/follow_the_money/`. Root `providers/` contains only provider manifests and fixture provenance, while `scripts/feed/` and `scripts/skill/` are thin executable wrappers. This prevents duplicate adapter implementations. A single `follow-the-money` console command exposes `feed`, `brief`, `eval`, and `replay` subcommands; wrappers call the same package functions.

Repository JSON Schemas use JSON Schema 2020-12 and are the serialized contract authority. Every persisted object carries `schema_version`; producer and consumer support the same declared major version and fail closed on unknown or incompatible versions. Repository config, JSON, LLM requests/responses, and canonical artifacts decode/encode as strict UTF-8. Raw provider bytes instead use only the owning verified manifest's exact allowlisted response charset with a strict decoder: no replacement characters, heuristic sniffing, or conflicting BOM/header/meta declarations. After that conversion, every repository string must contain only Unicode scalar values; lone high/low surrogates and category `Cs` are rejected before NFC, length measurement, canonical hashing, rendering, or replay. Objects are closed: an applicable numeric/reference/measurement value that is unknown is present as `null` plus a required closed `unknown_reason`; an applicable closed categorical field uses its literal `unknown` enum plus a required bounded `audit_reason`; neither form may be absent. An inapplicable field exists only in its applicable `oneOf` branch, and collections are present as arrays that may be empty rather than switching unpredictably between absent/null/empty. Units and status/reason values use closed enums. The four LLM response schemas—`resolver-output`, `analyst-output`, `editor-output`, and `language-audit-output`—are separate closed contracts restricted to the subset supported by OpenAI Structured Outputs, make every property required while representing optional non-categorical values with nullable unions, and set `additionalProperties: false`. Scripts validate those outputs, enforce references and field ownership, and merge only LLM-owned fields into the authoritative repository Event/Analysis/Brief/audit objects; an LLM never returns or replaces a repository object wholesale. Python models do not independently redefine incompatible contracts.

This is simpler than a service architecture and makes the same modules usable by CLIs, tests, evaluations, and GitHub Actions.

### 2. A provider protocol and explicit registry

Each provider implements `fetch(window, client)` and `normalize(raw, window)` and is loaded from an explicit configured registry. Provider exceptions are caught at the orchestration boundary and converted to structured source outcomes. No dynamic plugin discovery, dependency injection framework, or implicit fallback chain is introduced.

Every enabled adapter has a checked-in contract manifest that records fetch/redirect hosts, separately permitted evidence `source_link_hosts`, source terms/usage note and verification date, authentication/user-agent requirement, exact allowed response charset(s), pagination and an executable rate policy, source timestamp meanings, stable-record identity, units, freshness policy, fixture provenance, default-enabled status, and whether an empty result is valid for the requested window. Each source-link rule contains one canonical IDNA ASCII host, an explicit `allow_subdomains` boolean, an allowed-port set whose default is only HTTPS port 443, and a closed query policy listing allowed parameter names/value grammars plus tracking parameters to drop; a required cross-domain publisher or filing host must be declared by the owning provider rather than accepted globally. The closed rate policy declares a `scope_id`, positive token-bucket capacity/refill period, and non-negative minimum interval, or an explicit verified unlimited branch; manifests sharing a scope must declare the same policy. An adapter whose live contract is not verified remains disabled. A successful empty response, a partially invalid page, a retry-exhausted failure, and an intentionally skipped provider are distinct health states with item counters. A manifest-permitted empty result does not alone degrade a run when its configured coverage group remains satisfied; an unexpected empty result is incomplete, and a run with no accepted item from any enabled provider fails without replacing latest even when every transport request succeeded.

Provider clients contact only configured HTTPS hosts and allowlisted redirects, enforce response and decompression limits, use safe XML parsing, never dereference source URLs emitted by evidence, and redact credentials and sensitive headers from errors. Configured secret values must contain at least 8 UTF-8 bytes. Before an item may enter the Feed, its source URL is bound to its owning provider and canonicalized with a standards-compliant URL parser: scheme/host are lowercased, an IDNA host and a single trailing root dot are normalized, the default port is removed, the fragment is dropped, declared tracking parameters are dropped, and remaining query pairs follow the manifest's stable ordering/value grammar. Validation requires `https`, rejects userinfo, IP literals, percent-encoding in the authority/host, an undeclared non-default port, malformed IDNA, hosts outside the provider's exact or dot-boundary subdomain rule, unlisted query names/invalid values, and common/provider-declared credential parameter names. Every raw percent escape in path/query must be a complete `%[0-9A-Fa-f]{2}` triplet; a bare/truncated/non-hex `%` rejects the item. Before and after canonicalization, validation scans the exactly-once-percent-decoded path segments plus query names/values and rejects any case-sensitive substring equal to a loaded non-empty secret value, including an encoded path or a value with secret prefix/suffix. Any residual valid `%HH` escape after that single decoding step is rejected as ambiguous double-encoding rather than decoded recursively; suffix host lookalikes cannot match. Fragment material is discarded before persistence, and rejected raw/decoded material or secret values are never logged. Only this validated credential-free canonical URL is hashed, retained, or later rendered. Retries are bounded, honor `Retry-After`, retry only configured transient failures, and share an injected clock and deadline.

The shipped v1 limits are explicit configuration: 20 seconds per HTTP attempt, 3 total attempts, a 300-second Feed pre-commit deadline from command startup with a fixed 15-second irreversible-commit reserve, global provider-request concurrency 8, per-host concurrency 2, 10 MiB maximum decompressed response, 2,000 normalized items per provider, 300 title code points, 1,000 snippet code points, 2,048 URL characters, 260 observations per instrument, and a 50 MiB serialized Feed. V1 uses one exclusive Feed collection lock rooted in the explicit output root, acquired before reading latest or capturing a cutoff and held through provider collection and Feed publication; cooperating CLI processes that share a provider/rate scope must therefore share that output root, and cross-root concurrent use of the same scope is unsupported. Lock waiting uses the same injected monotonic deadline, occupies no provider-request concurrency slot, and fails typed `collection_lock_timeout` with no provider call or artifact if the deadline cannot admit acquisition.

The output root also holds a closed versioned durable rate-state registry plus one per-`scope_id` state, all protected by the collection lock and updated by same-directory atomic replace plus file/parent `fsync`. The registry records the output-root identity and every initialized scope/policy fingerprint with `initializing | active` status; each state records Decimal tokens/refill wall anchor, last-dispatch wall time, and cooldown. A genuinely new output root creates its registry once with atomic no-replace. A new scope is initialized through a recoverable two-phase sequence before any request: atomically add `initializing`, create/fsync the full-capacity state with injected UTC-now anchor, then atomically mark `active`. Recovery may complete an `initializing` entry only after validating that no request was admitted; an `active` registry entry with a missing/partial/unreadable/corrupt/unknown-schema state fails closed and can never reinitialize full. A missing/corrupt registry under an already marked persistent root likewise fails closed. A new scope absent from a valid registry may use that same two-phase initialization. A policy-fingerprint change never resets implicitly: an explicit offline migration under the same lock, with zero provider sends, sets the new state to zero tokens and a cooldown no earlier than both the old cooldown and injected now plus the new refill period before activating the new fingerprint. A new process may refill only from non-negative injected UTC elapsed time; wall-clock rollback grants no tokens and produces a typed wait/failure rather than resetting the bucket. Before request bytes may be sent, orchestration durably debits one token and installs the shipped conservative 24-hour crash cooldown. A confirmed pre-send failure may durably refund. After any controlled terminal outcome—including a complete response, HTTP error, connection failure, or timeout while the process remains able to update state—the debit remains but an atomic reconciliation replaces the provisional value with the greater of the manifest policy's next eligible time and a valid `Retry-After` when present; this permits only policy-compliant transient retry. Process crash, uncertain loss before reconciliation, or state-update failure retains the 24-hour cooldown, stops further requests, and protects restart. This makes sequential/crashed CLI runs preserve rate state instead of reloading a full bucket. Within the locked run, per-provider pagination is sequential unless its verified contract explicitly requires another order, and every pagination/retry request consumes this persistent shared policy before the per-host concurrency limiter. Every wait completes before taking a request-concurrency slot. Providers are admitted in provider-ID order; a rate wait that cannot fit the shared pre-commit deadline and reserve produces a typed outcome rather than violating the manifest. Completed results cannot mutate shared Feed output directly, and orchestration joins immutable outcomes in provider-ID order. Deadline expiry cancels queued/in-flight requests, ignores any late response for Feed mutation while retaining its durable rate debit, and reconciles state if the process can do so. A `Retry-After` or retry that cannot fit the remaining admitted request time plus reserve is not started. Limit violations become structured provider/item failures and are never silently truncated except for the explicitly bounded title/snippet fields, whose truncation metadata is retained.

All Feed planning, requests, normalization, validation, staging writes, and staging `fsync` must complete by monotonic second 285. Only then may the command enter the non-cancellable dated/latest rename-and-parent-`fsync` sequence. Once admitted, that filesystem transaction runs to its normal success/failure boundary even if elapsed time crosses second 300; a successful overrun remains success and reports `commit_elapsed_overrun` only in the post-transaction machine-readable command status/stderr, while any durability error follows the typed `commit_durability_unknown` rules. Neither outcome can be written into the already hashed immutable Feed candidate. If commit admission has not occurred by second 285, the run exits 1 without a dated/latest rename. Thus ordinary blocking filesystem calls never require unsafe timeout cancellation or retroactive rollback.

The initial free adapters target official/public Fed, BLS, SEC EDGAR, CFTC, PBOC, NBS, SSE/SZSE, Yahoo-compatible market data, and an optional AKShare adapter. Shipped v1 has this closed mandatory coverage matrix:

| Group | Required verified-and-enabled members/capability | Runtime minimum |
| --- | --- | --- |
| `us_official_macro_policy` | Fed and BLS, including their supported release/calendar contracts | 2 of 2 healthy |
| `us_company_filings` | SEC EDGAR watched-company filing contract | 1 of 1 healthy |
| `china_official_macro_policy` | PBOC and NBS official evidence contracts | 2 of 2 healthy |
| `china_exchange_evidence` | SSE and SZSE notice/market contracts | 2 of 2 healthy |
| `china_hk_cross_asset_market` | Yahoo-compatible contract with explicit source mappings/units/availability policy for all 13 configured dashboard roles, including CSI 300 and Hang Seng | 1 of 1 healthy, with missing roles recorded |
| `future_calendar` | Fed, BLS, and NBS future-release calendar capabilities | 3 of 3 healthy |

A member is healthy for group counting only when it succeeds with accepted items or returns a manifest-permitted empty result; disabled, skipped, unexpected-empty, partial, or failed members do not count. Missing required dashboard-role observations also mark that runtime group incomplete while retaining unavailable role records. A deficient mandatory group makes a non-empty Feed degraded rather than silently healthy; independently, zero accepted items remains failure. Fed, BLS, SEC EDGAR, PBOC, NBS, SSE, SZSE, and Yahoo-compatible adapters are shipped enabled only after their checked-in contract/capability verification succeeds. If any matrix row cannot be backed by the required verified enabled contracts and fixtures, shipped-default configuration validation and Apply completion fail rather than weakening the row or declaring a disabled placeholder complete. CFTC is enabled by default only after verification but is optional for matrix completion because positioning output is conditional. AKShare, BEA, HKEX, Tier 2 media, and paid enhancements remain disabled by default and cannot satisfy a row unless a later version explicitly changes the matrix after contract/implementation verification. Provider HTTP tests use recorded or authored fixtures and never depend on live network access.

### 3. One fixed cutoff prevents look-ahead

The scheduled Feed workflow starts near 08:20 Asia/Shanghai (`00:20 UTC`). Immediately before any provider request it captures one injected wall-clock `evidence_cutoff_at` and supplies that upper bound to every provider. It separately records `collection_started_at`, per-provider request/retrieval times, `collection_completed_at`, and `generated_at`, and validates `collection_started_at <= evidence_cutoff_at <= request/retrieved_at <= collection_completed_at <= generated_at` for applicable timestamps. Operational deadlines use an injected monotonic clock, not subtracting wall-clock timestamps. The Brief displays the fixed evidence cutoff and its later logical as-of/completion times; it never uses collection completion or a nominal 08:30 value as evidence coverage.

The evidence window is `[window.start, evidence_cutoff_at)` and MUST be strictly advancing. After acquiring the exclusive collection lock and before any provider call, a scheduled run checks `feeds/latest.json`: only an actually absent path is a first-run bootstrap; a present but unreadable, partial, schema-invalid, digest/run-ID-invalid, or otherwise integrity-invalid latest Feed is typed `invalid_latest_integrity`, makes zero provider calls/artifacts, and is never treated as missing. With a valid latest, the run captures its new cutoff and derives `window.start` from that cutoff. If the captured `evidence_cutoff_at <= latest.evidence_cutoff_at`, planning fails with typed `non_advancing_cutoff`, makes no provider call, and writes no dated artifact. The shipped v1 bootstrap lookback and excessive-gap threshold are both exactly 72 hours: only with an absent latest path, `window.start = evidence_cutoff_at - 72h`; when the new cutoff minus a valid latest cutoff is greater than 72 hours, the same bounded bootstrap start is used and a coverage-gap warning records the uncovered interval; an exact 72-hour gap still starts at the prior cutoff without a gap warning. A waiting cooperating run plans only after the prior run releases the lock and therefore re-reads the resulting latest Feed; it never continues from a pre-lock frozen window. CLI fixture mode requires explicit strictly ordered instants. Every payload separates source knowledge time, financial effective/reference time, and Feed selection basis as follows:

| Payload | Knowledge time used for cutoff | Effective/reference time and Feed selection |
| --- | --- | --- |
| `news` | source `published_at` or later `updated_at` for a revision | supported `occurred_at`, otherwise publication time; delta selected by knowledge time in the Feed window |
| `macro_release` | source `released_at` | release instant is effective; observation period is reference metadata; delta selected by release time |
| `policy` | source `published_at`/`announced_at` or later `updated_at` | explicit `effective_at` when sourced, otherwise announcement time; delta selected by knowledge time |
| `filing` | source acceptance/publication instant | acceptance/publication is event effective time; reporting period is reference metadata; delta selected by knowledge time |
| `flow` | source publication/availability instant | measurement `as_of` is effective/reference time; delta selected by knowledge time |
| `positioning` | report publication instant | report/measurement `as_of` is effective/reference time; the bounded current latest-report snapshot may precede `window.start`, but it must have been known before cutoff |
| `market_data` | observation `as_of` plus the manifest's conservative availability lag, or an explicit source `available_at` | observation `as_of`; current snapshot plus bounded older lookback observations may precede `window.start`, but every value must have been available before cutoff |
| `calendar` | source announcement/update time, or a manifest-defined conservative availability time | future `scheduled_at`; v1 fetches `[evidence_cutoff_at, evidence_cutoff_at + 26h)`, persists `calendar_horizon_end`, and may carry an unchanged item published before `window.start` when it was known before cutoff |

`retrieved_at` is audit metadata and never substitutes for source knowledge time. Unknown timestamp precision remains explicit: a delta item with no usable knowledge instant is rejected, while date-only knowledge is eligible only after that source-local date has fully elapsed; that end-of-local-date eligibility instant becomes its canonical knowledge instant. Post-cutoff publications/revisions and observations not yet source-available at cutoff are rejected. Every normalized source fact retains its script-owned `knowledge_available_at` derived only from this table. For a canonical Event, `fully_known_at` is the maximum `knowledge_available_at` across its exact `key_fact_ids`; it is distinct from the Event's economic effective/reference time and must not be supplied or changed by an LLM. The snapshot exceptions never authorize arbitrary historical Feed carry-forward: only configured bounded market lookbacks, the current bounded positioning report, and the configured future-calendar horizon are present in the newly fetched, validated latest Feed. All persisted instants are RFC 3339 UTC; `Asia/Shanghai` is a display and schedule zone.

The repository provides a Skill CLI but does not claim that GitHub Actions automatically invokes a user's local Codex Skill at 08:30. That automation is configured separately by the deployment environment.

### 4. Unified envelope with closed typed payloads

`feed.schema.json` defines the common envelope and a `oneOf` payload for `news`, `macro_release`, `policy`, `market_data`, `flow`, `positioning`, `filing`, and `calendar`. The envelope includes `schema_version`, `run_id`, the fixed window, collection timestamps, per-provider outcomes, and mandatory producer provenance: the same closed path/size/file-hash application-build descriptor used by run bundles, the canonical redacted resolved Feed-configuration snapshot and hash, the Feed-schema descriptor, and a sorted canonical redacted closed runtime-contract snapshot plus hash for every enabled provider, with optional Git metadata. The embedded provider snapshot includes all non-secret fetch/redirect/source-link/rate/time/identity/unit/freshness/empty-window rules needed to validate its normalized items and outcome; authentication values and other secrets are never included. The producer computes these descriptors/snapshots from its local files at generation; every snapshot/hash participates in the canonical content digest. A consumer recomputes internal aggregate hashes from the embedded closed descriptors/snapshots, uses the embedded provider contract—not a current local manifest—to revalidate item provenance/source URLs, and validates Feed identity and supported schema major without requiring producer fingerprints to equal the current consumer build/config. They bind declared provenance to the content rather than proving unseen producer application bytes or signer authenticity. Feed items contain evidence/facts and raw metadata only. Intelligence fields such as importance, direction, price-in, regime, impact, and ranking are rejected.

Market-data payloads may contain a configured bounded `observations` array fetched in the same run. These are raw timestamp/value/volume facts, not calculated intelligence. Duplicate timestamps with different values are a provider conflict; exact duplicates collapse deterministically, and serialized observations are strictly chronological. They allow rolling volatility and z-score calculation while preserving latest-only Skill consumption. Normalized surprise uses only a versioned configured scale; the initial repository does not imply unavailable historical consensus data.

### 5. Deduplication preserves corroboration

Feed generation removes exact normalized URLs and same-source near duplicates. Canonical URL duplicates across sources retain one deterministic survivor plus every source-lineage record; they do not count as independent corroboration when they share an original publisher or wire story. Distinct independently originated reports remain separate evidence. During Skill preprocessing, similar evidence is linked into candidate blocks and canonical events while every original evidence identity and provenance relationship remains auditable.

V1 title similarity is closed: NFC normalize, Unicode-casefold, remove every Unicode punctuation/separator/control code point, take overlapping Unicode-code-point trigrams, and calculate Jaccard intersection/union; when either normalized title is shorter than three code points, only exact normalized equality scores 1 and every other pair scores 0. No locale/tokenizer/model heuristic participates. Candidate graph roots are only deterministic fact mentions whose fact IDs qualify as `atomic_event_seed_fact_ids`, not whole evidence items or every ledger entry: one root node is `(evidence_id, seed_fact_id, normalized subject-or-unresolved-subject key)`. A multi-entity bridge therefore contributes distinct seed-mention nodes and the fact-projected evidence may appear in multiple components, but its mentions receive no edge merely because they share an evidence item. A non-seed fact may be attached as supporting input only to each seed component containing the same evidence ID, is bounded by that component's bytes/reference limits, and never creates an edge or component. Unattached `market_data`, `calendar`, `OBSERVATION`, `INFERENCE`, or other non-seed facts remain available to the deterministic ledger/dashboard/watchlist/packet stages but never consume resolver records, seeds, blocks, or output coverage.

Two mention nodes receive an undirected edge only through one of these v1 rules using `knowledge_available_at`: (a) their complete canonical fact keys excluding source lineage are equal; (b) they share an exact resolved entity, are at most 48 hours apart, and either share the exact predicate/category or have title Jaccard at least `0.45`; or (c) neither has a resolved entity, they share exact market and category, are at most 12 hours apart, and title Jaccard is at least `0.85`. Different non-empty entity sets never connect only through title/time. These thresholds and predicate/category normalizations are versioned configuration with exact boundary fixtures. The resolver receives each component's fact allowlist plus the corresponding bounded evidence projection, so bridge text may supply context but cannot assign a fact from another component. Identical proposals arising from repeated bridge evidence collapse only by the later canonical Event ID; ambiguous relationships remain unresolved rather than force-merging components or Events.

### 6. Deterministic identities and ordering

Feed item IDs are stable hashes of provider identity plus normalized source record identity. Candidate component IDs hash sorted mention-node IDs. Candidate block IDs hash the ordered packed component IDs plus each component's sorted projected `(evidence_id, allowed_fact_ids)` records and boundaries, so the same bridge evidence set with different fact allowlists cannot collide. Canonical event IDs hash a versioned canonical tuple of sorted evidence IDs, event type, normalized resolved entity IDs, and an atomic discriminator formed from the sorted complete canonical keys of the event-defining facts. Each discriminator fact key contains its normalized subject entity ID or stable normalized raw-subject identity, predicate, economic effective/reference instant or date plus precision/granularity, normalized object/value, and unit; this preserves subject-value and fact-time binding in multi-fact Events. Source fact IDs themselves are not substituted because their provider/evidence lineage would add identity noise already represented by sorted evidence IDs. Titles, summaries, and other free LLM text are excluded. The canonical serializer defines Unicode normalization, decimal-string encoding, key ordering, hash algorithm, and collision failure. Scripts validate `fully_known_at` as the exact maximum knowledge instant of the Event's `key_fact_ids`. Event schema retains the sorted per-key-fact economic time values; it exposes `common_effective_time` only when every key fact has the identical normalized value and precision/granularity, otherwise that nullable projection is `null` with `multiple_effective_times`. No ranking uses that optional projection. The LLM cannot choose IDs, knowledge/effective instants, or event labels. A versioned script template derives each Chinese display label only from the closed event type, resolved entity display names, and structured values/units of the Event's existing `key_fact_ids`; unsupported/free-text resolver titles are not a field, and the label retains the exact fact/evidence references used by the template.

All script rankings use the Event's single script-owned `fully_known_at` information time and stable ID as their exact time/identity tie-breakers; a multi-fact economic-time projection never participates. Input-order stability is guaranteed for the same validated semantic outputs and versioned configuration; live model calls are not claimed to be bit-for-bit reproducible.

### 7. Evidence Ledger is the immutable boundary

Before resolution, scripts extract source-derived candidate ledger entries with stable fact IDs and types `FACT`, `CLAIM`, or `OBSERVATION`; script-derived calculations may add `INFERENCE` entries with deterministic parent IDs. The resolver may assign only existing candidate fact IDs and evidence IDs to an event proposal. Each proposal must identify at least one event-defining fact ID, and proposals split from one evidence item must have distinct event-defining fact-ID sets; if the source evidence cannot be deterministically separated into existing fact records, the resolver must abstain instead of inventing a discriminator. Canonical-event scripts then freeze the event-specific ledger and its shared supporting entries. The canonical Event's script-owned `key_fact_ids` is exactly its sorted, deduplicated `event_defining_fact_ids`; supporting ledger facts remain auditable but cannot enter the authoritative fact summary or a confidence/full-event gate as an undeclared key fact. LLM-produced mechanisms, implications, and interpretations live only in the separate Analysis object and reference ledger/evidence IDs already present in their verified packet; they never append to the ledger. A versioned fact key identifies comparable subject, predicate, effective time, value, and unit; incompatible values are retained as conflicts, and numeric tolerances are explicit configuration rather than hidden equality. Unknown references or attempts to mutate Event facts fail schema and semantic validation.

Canonical events are runtime objects and are not written back to GitHub Feed artifacts.

Field ownership is closed: providers and Feed scripts own source facts/provenance; resolver output owns only candidate-existing evidence/fact membership, the event-defining membership proposal, and closed non-prose event attributes; canonical-event scripts own IDs, the exact `key_fact_ids = event_defining_fact_ids` projection, fact-referenced deterministic display labels, and the frozen ledger; the analyst owns only the separate mechanisms, implications, bounded reaction attributions, price-in assessments, indirect indications, asset mappings, watch points, alternative interpretations, categorical features, the closed China/Hong Kong and US exposure categories, and membership drawn from existing deterministic watchlist IDs; scoring/selection/money-flow merge scripts own every numeric score, gate, penalty, and final status; the editor owns only schema-bounded wording; renderer and script audit own output structure, the claim inventory, and deterministic publication checks; the language auditor owns finding categories but not severity or publication.

### 8. Candidate blocking precedes semantic resolution

Scripts form the exact mention-level candidate graph above and take its connected components. A component's stable key is the hash of its sorted mention-node IDs, and its resolver projection deduplicates then sorts `(evidence_id, allowed_fact_ids)` records only within that component; the 20-item count applies across the packed projections, so a bridge projection in two components remains two boundary-separated records and counts once in each. V1 sorts components by the stable key ascending and uses non-reordering next-fit packing: append the next whole component to the current block only if every post-append bound remains satisfied; otherwise close that block and start the next. A packed request preserves each component alias and projection boundary, and every resolver proposal/unresolved group belongs to exactly one component and may use only its references. The shipped v1 resolver-block dynamic-data limits are 20 projected evidence records, 24 total `atomic_event_seed_fact_ids`, and 32 KiB of canonical UTF-8 bytes, with at most 40 blocks; no tokenizer estimate participates. A connected component that itself exceeds any bound cannot be split without losing a possible cross-partition relationship, so normal mode fails typed `candidate_group_too_large` before resolver calls rather than truncating or asserting completeness. More than 40 resulting blocks is a typed `capacity_exceeded` normal-mode failure. The semantic resolver sees every validated sorted block within capacity rather than a pre-resolution shortlist or all item pairs, preventing evidence loss and quadratic LLM clustering. After canonical events and their packets exist, the v1 analyst shortlist takes at most 20 passed packets ordered by evidence confidence `High > Medium > Low`, then maximum available absolute normalized surprise across the Event's `key_fact_ids` descending with unknown last, `fully_known_at` descending, and event ID ascending. This pre-analyst key deliberately excludes reaction z-scores because event/asset mappings are analyst-owned; it only bounds analyst calls and is not Event Significance. Non-shortlisted events remain in the audit trace but cannot enter full or compact final selection without a valid analysis. A bridge item may support multiple atomic events; the resolver partitions every deterministic seed into one proposed or unresolved Event membership, returns closed attributes rather than prose, and may return unresolved when the supplied title/snippet cannot support extraction.

The resolver is prohibited from impact analysis, direction, price-in, importance, and ranking. “Verification” means script-side completeness, cross-reference, provenance, conflict, and schema checks against the already collected Feed only. The Skill performs no post-cutoff network fetch; unsupported facts remain unresolved.

### 9. One OpenAI adapter, four constrained passes

Use one OpenAI Responses API adapter and one configured compatible model value for:

1. semantic event resolution;
2. shortlisted verified-packet financial analysis;
3. structured editorial synthesis, including bounded explanations of the already classified market state and watchlist;
4. final claim-language audit of the deterministic render.

The editor never receives complete verified packets, full Analysis objects, or URL targets. Scripts build one ordered editor projection from the at-most-61 editor-fillable claim slots. Each slot contains its request-local alias, closed slot kind, required/optional and factual/causal flags, at most 768 canonical UTF-8 bytes of already validated structured source values or analyst-owned text, and at most 8 existing reference aliases; outer identity/order/config data is capped at 4 KiB. The conservative complete projection bound is `61*(768 + 8*11 + 160) + 4096 = 66,072 < 73,728` bytes. Equality with the 72-KiB dynamic cap passes; a slot or projection one byte/ref over fails `editor_input_capacity` before the call without truncation. Checked-in all-max fixtures prove every legal 12-event/61-slot allocation is representable.

The v1 editor allocation and projection are closed rather than implementation-selected. ### 10. Deterministic market analytics and observability

Scripts calculate daily/session simple returns, yield basis-point changes, volume changes, rolling volatility, standardized abnormal moves, and cross-asset breadth from raw observations aligned to configured completed sessions. Before constructing `Decimal`, adapters lexically bound every raw numeric token to 64 ASCII bytes, at most 24 significant digits, and any base-10 exponent to `[-12, 12]`, rejecting hexadecimal, binary float special values, booleans, locale separators, or excess digits/exponents. Persisted Feed/runtime financial values use only canonical plain decimal strings matching `-?(0|[1-9][0-9]*)(\.[0-9]+)?`, with no exponent and no negative zero, still at most 64 bytes/24 significant digits and absolute magnitude at most `10^18`. Every verified provider manifest supplies a closed inclusive domain per numeric field/unit within that common guard; missing domains prevent enablement. Shipped common types require price/index/FX/commodity/crypto levels `>0`, volume/open-interest/count levels `>=0`, allow signed flow/position/change fields only within their declared domain, and allow negative yield/rate/percentage values only within their declared domain. Inputs outside the lexical/common/field domain are rejected before arithmetic rather than converted to `unknown`; a mathematically unavailable dependent metric from otherwise valid domain inputs may become `unknown` under the formula rules.

Every v1 calculation runs inside a fresh local Decimal context, never the process-global context: precision 50, `ROUND_HALF_EVEN`, `Emin = -999999`, `Emax = 999999`, `clamp = 0`, with `InvalidOperation`, `DivisionByZero`, `Overflow`, and `FloatOperation` trapped. The normative operation order is explicit: arithmetic follows the written parenthesization; mean is stable-order `sum(x_i) / n`; sample variance is stable-order `sum((x_i - mean) * (x_i - mean)) / (n - 1)`; sample standard deviation and annualization factors use `Decimal.sqrt()` in that same context; z is `(current - mean) / std`; and weighted scores multiply each canonical component then sum in configuration order. The resulting precision-50 context value—not a serialized quantization and not an ambient-context value—is the canonical value used for bins, gates, thresholds, and sorting. Output quantization happens only afterward at the documented boundary. Hostile-global-context and adjacent-threshold fixtures are normative.

The v1 calculation contract is: simple return `(current / previous - 1)`; yield change `(current_percent - previous_percent) * 100` basis points; volume change `(current / previous - 1)`; rolling volatility is the sample standard deviation of the preceding 20 consecutive completed-session simple returns with `n-1` denominator, annualized by same-context `sqrt(252)` for configured exchange-traded and 24/5 instruments and `sqrt(365)` for 24/7 instruments. A price abnormal-move z-score compares the current simple return with the mean and sample standard deviation of those preceding 20 returns; a yield abnormal-move z-score compares the current basis-point change with the preceding 20 consecutive completed-session basis-point changes. Both exclude the current observation from their reference window. Directional breadth is `(positive_count - negative_count) / observable_count` over the configured universe and completed session. Equity/ETF returns use source-supported split/dividend-adjusted closes; an adapter without a verified adjustment contract cannot supply comparable return inputs. Returns, volume changes, volatility, both z-score types, and breadth serialize to 6 decimal places; yield changes serialize to 2 basis-point decimal places; they are formatted as percentages only by the renderer. A missing required session/change (holidays excluded by the configured calendar), non-positive denominator, fewer than 20 consecutive reference changes, zero reference standard deviation, incompatible unit, or zero observable count yields `unknown` with a reason; missing sessions are never skipped or forward-filled to manufacture a window. Formula parameters, unit conversions, local context, operation order, and precision remain closed validated versioned configuration matching these v1 defaults and have hand-calculated oracle fixtures.

Reaction observability uses the canonical Event's script-owned `fully_known_at` as its sole information-release anchor, plus the configured asset session, exchange calendar, and available observation timestamps; the distinct economic effective/reference time remains metadata and never moves the reaction window before or after disclosure. For v1 daily data, the measurement is the first completed affected-asset session whose close is strictly after `fully_known_at`, compared with that session's immediately preceding valid close; knowledge at or after a session close rolls to the next completed session, and no result is observable until both closes were source-available before the Feed cutoff. A 24/7 asset uses the first configured UTC daily boundary strictly after `fully_known_at`, while 24/5 instruments use their configured calendar boundary. It returns `observable` or `not_observable` with anchor/measurement timestamps and a reason. This is a session-level observation and must not imply intraday causality. Date-only knowledge, holidays, after-close announcements, stale observations, and missing sessions cannot be treated as zero reaction.

### 11. Surprise and confidence abstain when evidence is absent

Raw surprise is `actual - consensus` only when both are compatible numeric facts. Normalized surprise is `raw_surprise / configured_positive_scale` only when a versioned per-series scale exists; otherwise it is `unknown`. Shipped v1 defines only these exact percentage-point scales: US all-items seasonally adjusted CPI month-over-month `0.1`, US core PCE price index month-over-month `0.1`, and US PPI final demand seasonally adjusted month-over-month `0.1`. Series identity, seasonal adjustment, and frequency must match exactly; all other series remain `unknown` until an explicit versioned scale and oracle are added. The LLM never supplies consensus, scale, series identity, or arithmetic.

Evidence confidence is independent of significance and is computed first for every script-owned `key_fact_id`, then conservatively aggregated as the lowest key-fact confidence. For one key fact, with no unresolved material conflict, at least one Tier 1 source or two independently originated Tier 2 source families yields High; exactly one Tier 2 source family yields Medium; Tier 3-only support yields Low; no support yields unresolved. Any unresolved key fact makes the Event unresolved and excludes it. A material conflict caps the affected key fact and therefore the Event at Medium until the verified packet resolves it or explicitly carries the conflict. Duplicate URLs, mirrors, and syndicated copies from one original publisher count once. Low confidence cannot enter the full-event set as confirmed fact; it may appear only as clearly labelled breaking/unconfirmed material.

Medium-confidence full-event eligibility is not a second network lookup. It requires a deterministic packet-completeness gate over every Event `key_fact_id`: each has an in-Feed evidence reference and a canonical source URL revalidated against the exact owning-provider contract snapshot embedded in that Feed, no material conflict is unresolved, all numeric units agree, and the packet records `verification_status = passed`. The authoritative fact summary may render only those declared key facts. Failure excludes the event from the full-event set without upgrading confidence.

### 12. Bounded semantic features become deterministic scores

The analyst may return categorical `scope`, `fundamental_depth`, `reversibility`, and `structural_horizon`, including `unknown`, plus audit reasons. Scripts map those categories to Fundamental Magnitude and Persistence. They also calculate Surprise, Systemic Breadth, and Repricing Magnitude.

All score components are on a closed `0..100` scale. `scoring.yaml` exhaustively defines categorical mappings, normalized-surprise and abnormal-move bins, systemic-breadth rules, morning-relevance weights, Brief Priority formula, quality thresholds, confidence gates, target counts, and redundancy penalty. It defines the initial significance weights 30/20/20/20/10. The v1 missing-data policy preserves the full denominator, contributes zero for an unknown component, records component coverage as the sum of configured weights whose whole component is known divided by the total configured significance weight, and requires at least 60% coverage for every normally selected full or compact event; weights are never silently reallocated. Fundamental Magnitude is known only when both `scope` and `fundamental_depth` are non-`unknown`, and Persistence only when both `reversibility` and `structural_horizon` are non-`unknown`; otherwise that whole component is unknown and contributes zero. Decimal intermediates are retained and final scores are quantized only at the documented boundary. The shipped v1 configuration and hand-calculated score vectors are normative fixtures, while future value changes require a version and regression comparison.

The shipped v1 mappings are fixed rather than chosen during implementation: `scope = single_entity:25, sector:50, single_market:75, cross_market:100, unknown:0`; `fundamental_depth = headline:25, operating_or_policy:50, balance_sheet_or_liquidity:75, systemic:100, unknown:0`; persistence contributions are `reversibility = high:25, medium:50, low:75, effectively_irreversible:100, unknown:0` and `structural_horizon = intraday:0, days:25, weeks:50, months:75, years_plus:100, unknown:0`. The Event Surprise component uses the maximum absolute normalized surprise among available values attached to its `key_fact_ids`; unknown key-fact surprises are ignored when another is available, and no available value makes the whole component unknown. That aggregate and maximum observable absolute reaction z-score use bins `<0.5:0`, `<1:25`, `<2:50`, `<3:75`, and `>=3:100`.

V1 has exactly nine independent `asset_group` values and deterministic reaction proxies: `cn_hk_equities -> {CSI 300, Hang Seng}`, `us_equities -> {S&P 500}`, `us_rates -> {US 2-year yield, US 10-year yield}`, `china_rates -> {China 10-year yield}`, `usd_fx -> {DXY, USD/CNH}`, `industrial_commodities -> {copper}`, `energy -> {WTI}`, `precious_metals -> {gold}`, and `crypto -> {BTC}`. Every mapping has exactly one `direction = positive | negative | mixed | unclear`, `confidence = high | medium | low | unknown`, `horizon = intraday | next_session | days | weeks | months | years_plus | unknown`, one non-empty at-most-192-byte `mechanism`, 1..8 existing packet reference aliases, and a required nullable at-most-192-byte `audit_reason`. `audit_reason` must be non-null when direction is `unclear` or confidence/horizon is `unknown`, and must be null otherwise. Systemic Breadth is `affected_groups / 9 * 100`, and an affected group requires its single validated non-`unclear` mapping. The component is known only when at least one mapping is non-`unclear`; no mappings or only `unclear` mappings make it unknown rather than zero. Repricing Magnitude uses the maximum observable absolute current-excluded reaction z-score among the deterministic proxies for mapped groups and is unknown when no mapped proxy is observable. The Growth regime's equity breadth universe is exactly S&P 500, CSI 300, and Hang Seng; zero returns are observable in the denominator but neither positive nor negative.

Morning Relevance weights freshness, China/Hong Kong open relevance, US next-session relevance, and unresolved next-24-hour catalyst at `40/25/20/15`. Freshness age is `evidence_cutoff_at - fully_known_at`, never age from the economic effective/reference time; a date-precision fact uses the end-of-source-local-date eligibility instant already stored as its knowledge time. A missing knowledge time makes the Event invalid, and `fully_known_at > evidence_cutoff_at` is look-ahead and fails validation rather than scoring as fresh. Freshness maps age `<=6h:100`, `<=12h:75`, `<=24h:50`, `<=48h:25`, older:0`. The analyst output has two required closed referenced categories, `cn_hk_exposure` and `us_next_session_exposure`, each `direct | indirect | none | unknown`; scripts alone map them to `100 | 50 | 0 | 0`. The analyst may return only a subset of those existing IDs as `catalyst_calendar_ids`; scripts validate every ID/reference and map non-empty to 100 and empty to 0, without parsing free-text watch points. Brief Priority is `0.70 * significance + 0.30 * morning_relevance` before confidence/coverage gates and redundancy deductions. Initial minimum component coverage is 60%, full-event priority is 60, compact-event priority is 40, and the routine same-family penalty is 15. Gates compare unquantized Decimal values; serialized component and final scores use 2 decimal places.

### 13. Ranking is deterministic and quality-first

Scripts execute one normative selection pipeline. First compute Event Significance, Morning Relevance, and `base_priority = 0.70 * significance + 0.30 * morning_relevance`; unresolved events, events without valid analysis, and events below 60% significance-component coverage are ineligible. High and packet-passed conflict-free Medium events are full-capable; High, packet-passed conflict-free Medium, and clearly labelled Low events are compact-capable, while unresolved events are neither. Sort eligible events by base priority descending, `fully_known_at` descending, then event ID ascending. Within that frozen order, the first event of each script-derived non-singleton story family receives no routine penalty and each later member receives 15 points unless the exact unordered Event-ID pair between it and that frozen first member carries validated `distinct_material_development`; unknown or singleton families are Event-ID-specific singletons, coexistence is non-transitive, and a pair between two later members does not exempt either from the first-member comparison. Set `final_priority = max(0, base_priority - penalty)`, then discard events that meet neither their full threshold 60 nor compact threshold 40, and sort survivors by final priority descending, `fully_known_at` descending, then event ID ascending. Take the first 12, assign full format to the first up to 3 selected full-capable events with `final_priority >= 60`, and render every other selected compact-capable event with `final_priority >= 40` compactly; a full-capable event outside the first three remains compact. Categories have no quotas. The v1 target of 10 is an informational product target only: it never truncates an 11th/12th qualifying event, fills a sparse result, or changes a threshold. Zero, one, or two total selected events receive a visible sparse-result warning. Related systemic-crisis events may coexist only through the exact pair and threshold rules above.

### 14. Market state is derived before narrative explanation

The v1 dashboard roles are S&P 500, CSI 300, Hang Seng, VIX, US 2-year yield, US 10-year yield, China 10-year yield, DXY, USD/CNH, copper, WTI, gold, and BTC; an unavailable role remains visible as unavailable and does not get a substitute instrument without a versioned configuration change. A dashboard move is highlighted as anomalous when its absolute current-excluded z-score is at least `2.0`.

The market engine maps available v1 signals to votes `supportive = +1`, `neutral = 0`, or `adverse = -1` using `z >= 0.5`, `-0.5 < z < 0.5`, and `z <= -0.5`; exact `+/-0.5` belongs to supportive/adverse. Risk Appetite votes are S&P 500, CSI 300, and Hang Seng z in their natural direction plus inverted VIX z, and the dimension is known with at least 2 of 4 votes. Rates uses inverted US 2-year, US 10-year, and China 10-year yield-change z and is known with at least 1 of 3. Liquidity uses inverted DXY and USD/CNH return z and is known with at least 1 of 2. Growth uses copper return z plus directional cross-market equity breadth, where breadth `>=0.20`, `<=-0.20`, or between maps to `+1`, `-1`, or `0`, and is known with at least 1 of 2. Inflation uses inverted WTI return z plus separate inverted votes for the latest in-window CPI, PCE, and PPI normalized surprise of each series, and is known with at least 1 of 4. Each known dimension is the sign of its vote sum; an exact zero sum is neutral.

The regime coverage denominator is the five dimensions. V1 returns `unknown` unless Risk Appetite is known and at least 4 of 5 dimensions are known. Otherwise rules are evaluated in this non-overlapping order: `risk_off` when Risk Appetite is `-1` and the known-dimension sum is `<= -2`; `risk_on` when Risk Appetite is `+1` and the sum is `>= 2`; `neutral` otherwise, including exact ties. An invalid configuration that makes rules overlap fails before classification. The LLM may explain but cannot select or change the state, and regime is informational: it does not alter event scoring, confidence, or selection.

### 15. Direct flow and indirect indications remain distinct

Scripts own the final money-flow merge. Typed `flow` or `positioning` evidence produces `money_flow.status = confirmed`; otherwise the analyst may return only an `indirect_indication` backed by referenced non-price evidence, which scripts may map to `indicated`; all other cases are `no_evidence`. The analyst cannot assign `confirmed`, and price movement alone always produces `no_evidence`. The optional Money Flow & Positioning section appears only when confirmed or clearly labelled indicated evidence survives audit.

### 16. Structured synthesis followed by deterministic rendering

The editor returns only `editor-output.schema.json`: bounded wording fragments and references for the already selected event explanations, preclassified market state, deterministic watchlist, and Bottom Line. It cannot return authoritative facts, numeric scores, statuses, URLs, ordering, or section membership. Before the editor call, scripts allocate a closed ordered set of claim-bearing slots for the already authoritative runtime objects. A stable `claim_id` derives from schema version, section key, owning Event/instrument/calendar ID, slot kind, and deterministic ordinal, excluding prose. Each slot has script-owned `is_factual` and `is_causal` flags and accepts at most one wording fragment; the editor may fill or leave only permitted optional slots and may not merge, split, reorder, reclassify, or invent a claim slot. Required unfilled slots fail assembly. Optional unfilled slot definitions remain only in the allocation trace; the authoritative `claim_inventory` contains exactly the filled slots that render, and each is one audit and metric denominator unit regardless of punctuation or clause count. Claim-bearing slots cover rendered dashboard observations, event fact summaries, mechanisms/implications, reaction attribution, price-in and flow statements, asset mappings, market-state/watchlist explanations, and Bottom Line points. Fixed section headings, field labels, source URLs, provenance metadata, and visibility warnings are not claims; event display labels are likewise non-inventory because scripts derive them exactly from closed structured facts, retain the contributing fact/evidence references, and audit that derivation instead of accepting prose. Scripts validate and merge the wording into those slots in the authoritative `brief.schema.json`, then a deterministic renderer produces the fixed Chinese heading order `市场仪表盘`, `市场状态`, `重点事件`, `其他重要事件`, optional `资金流与持仓`, `未来 24 小时关注`, and `结论`, with compact formats for up to three full events versus other key events. It displays the fixed evidence cutoff, generation time, source URLs, confidence, uncertainty, sparse-state notices, and stale/degraded warnings.

All editor-owned narrative slots declare `zh-CN`. After NFC normalization and removal only of configured allowed ticker/acronym/Latin proper-name and numeric/unit spans, each non-empty narrative fragment must contain at least two Han code points and, when at least four letters remain, Han code points must be at least 25% of those letters. This deterministic minimum rejects an all-English Brief while allowing source tickers and proper names; the language audit separately treats `wrong_language` as critical. The renderer alone creates headings, lists, and links. Every source/editor text fragment is canonicalized to one line by collapsing permitted whitespace runs to one ASCII space and stripping leading/trailing whitespace, and rejects Unicode categories `Cc`, `Cf`, `Cs`, `Zl`, and `Zp` (therefore C0/C1, lone surrogate/category-Cs values, bidi override/isolate, zero-width, and Unicode line/paragraph separators). Rendering treats it as a text node: `&`, `<`, and `>` become HTML entities, then every remaining ASCII punctuation code point in ranges `U+0021–U+002F`, `U+003A–U+0040`, `U+005B–U+0060`, and `U+007B–U+007E` receives a backslash. This covers fences, setext markers, links, and other CommonMark constructs; raw HTML and input-supplied Markdown/link syntax are never emitted. Only a canonical credential-free HTTPS URL already bound to its evidence's owning provider and revalidated against that Feed's embedded provider contract may enter a renderer-owned fixed-label link/autolink target after unsafe URL characters are percent-encoded. Renderer bytes are deterministic fixtures.

The renderer and validator also reject structured instruction fields and a versioned Chinese/English safety lexicon for direct buy/sell/add/reduce/position-size/entry/exit/stop/target instructions, while fixtures protect legitimate descriptive false positives. Asset mappings are limited to direction, confidence, mechanism, horizon, and evidence references. The v1 watchlist accepts only configured `critical` or `high` calendar priorities, sorts priority (`critical` first), then `scheduled_at` ascending and stable calendar ID ascending, and takes at most six without filling from lower priorities. These deterministic language/safety boundaries are backed by the language audit but do not claim finite script/lexicon rules can detect every possible paraphrase.

When `--degraded-report` is explicitly requested because an LLM pass cannot run, the CLI emits a separate `deterministic_degraded_report` object and Markdown, not a normal Brief. It contains only Feed health, dashboard facts, deterministic analytics, unresolved candidate counts, cutoff/provenance, and safety warnings; it omits event interpretations, price-in, causal attribution, asset implications, Bottom Line conclusions, and any field that requires an LLM. Every human-readable degraded heading/label/warning comes from a closed script-owned `zh-CN` template. Any retained provider/source label is still untrusted text and goes through the identical NFC/one-line whitespace, `Cc`/`Cf`/`Cs`/`Zl`/`Zp`, CommonMark/HTML text-node escaping, and instruction checks used by the normal renderer; links use only the input Feed's embedded owning-provider contract validation and renderer-owned labels. The degraded object/Markdown must pass the same schema, reference, URL, numeric, Unicode/rendering, language-template, and instruction audits, with adversarial snapshots, even though it does not run the editor or language-audit LLM.

### 17. Two-layer claim audit is fail-closed

After deterministic rendering, script audit verifies the closed claim inventory, exactly one rendered fragment per filled claim slot, deterministic event-label template output and its fact/evidence references, provider-bound URL presence against the saved Feed's embedded contract snapshots, evidence and ledger references, numeric provenance, Feed freshness, schemas, price-in support, direct-flow support, section structure, and prohibited instructions. Every claim-bearing output must have one known `claim_id`; no rendered assertion may exist outside the inventory. Any violation blocks that candidate artifact; it is never silently deleted in place. A corrected artifact must be regenerated and pass the complete audit sequence.

The final LLM audit receives the complete ordered claim inventory and a deterministic audit projection of every rendered heading, label, warning, and claim fragment in exact render order. The projection replaces each already script-validated HTTPS target with its request-local alias and retains the fixed visible link label; URL safety remains solely a script-audit responsibility. It therefore preserves all auditable language and claim-to-render mapping without spending model context on long URL targets. V1 deterministically renders at most one representative source link per dashboard role, selected Event, and watchlist item, chosen from that object's referenced evidence by source tier `Tier 1 > Tier 2 > Tier 3`, then `knowledge_available_at` descending and evidence ID ascending; all additional evidence references remain in the claim inventory and bundle. The complete actual Markdown is capped at 96 KiB and the audit projection at 72 KiB; equality passes, one byte over fails before the audit call without truncation. The language auditor checks every `claim_id` for causal overstatement, fact/inference confusion, unsupported conclusions, wrong language, and uncertainty wording, and cannot modify facts. It returns explicit covered claim IDs plus findings that reference existing claim IDs and evidence; missing/duplicate/unknown coverage fails semantic validation. Scripts apply the v1 severity mapping and own the publication decision. `causal_overclaim`, `inference_as_fact`, `unsupported_conclusion`, `fact_modification`, `trading_instruction`, and `wrong_language` are critical; `excessive_certainty` and `missing_uncertainty` are warnings unless they also satisfy a critical category. Any critical finding blocks normal publication, while warnings remain visible in Brief metadata. Because the same configured model generates and audits language, this is a bounded editorial check rather than independent assurance.

### 18. Evaluation separates deterministic and live evidence

The offline runner consumes at least 30 unique versioned golden trading-day Feed fixtures, recorded resolver/analyst/editor/audit outputs, and expected labels. It exercises schemas, deterministic stages, replay, and fixed input permutations without network or credentials. Provider changes are evaluated through raw-response adapter fixtures with contract provenance. Every report records the mandatory application build fingerprint described below; an available Git SHA/dirty flag is supplementary and never substitutes for it. An explicit credentialed live mode re-runs the same golden inputs through the configured prompts/model under declared repetition, request-attempt, monotonic-time, and cost budgets, stores each validated response locally, and compares distributions and per-run drill-downs; it is never a CI dependency and does not claim bit-for-bit model repeatability.

Live cost control requires an explicit local versioned/fingerprinted price table for the exact requested model with source URL/effective date, a closed set of permitted returned canonical model IDs/aliases using the same rates, and Decimal USD-per-million input/output-token rates; it never fetches or silently updates prices at runtime. The declared request/time/`max_cost_usd` budgets cover the entire live-evaluation invocation across every golden day, repetition, pass, and retry. To make budget winners and retries uniquely reproducible, v1 live evaluation intentionally uses LLM concurrency 1 and admits logical invocations in stable day/date, repetition-index, pass, resolver-block/analyst-Event ID order; within one invocation, attempt 1 precedes a conditionally eligible attempt 2. Before every API attempt, the evaluator atomically debits a worst-case reservation using that pass's conservative one-token-per-complete-request-byte reservation and maximum output tokens. The call is not sent when committed spend plus the new reservation would exceed `max_cost_usd`; equality is allowed. A failure proven to occur before request bytes were sent releases the reservation. Once dispatch may have reached the service, connection loss, timeout, or any HTTP error envelope retains the full reservation as committed worst-case spend; usage-like fields in an HTTP error are never trusted, and a retryable `408|409|429|5xx` may retry only when the remaining global request/time/cost budgets admit it. A received Responses API response object (`completed`, `refusal`, or `incomplete`) must identify a returned model in the price table's allowed exact set, carry valid total input/output usage within the reservation, and report zero reasoning tokens. Only then does actual spend atomically replace the reservation, calculated from all reported input tokens at the input rate and all output tokens at the output rate without assuming cache discounts. A model mismatch, nonzero/missing reasoning detail, missing/invalid usage, or usage above reserved bounds retains the full reservation and becomes `budget_integrity_failure`. Request budget counts every dispatched attempt, including retries, and the global monotonic-time budget must also admit the full attempt timeout. Canonical precision-50 Decimal drives gates and 6-decimal USD is serialization only. Any request/time/cost admission or budget-integrity failure stops with machine-readable `incomplete`, exit 1, and no complete-comparison claim. Reports label cost as a pinned-local-price-table estimate rather than provider billing truth.

Expected-event matching uses stable expected IDs or an explicit one-to-one alias map. Per-day Major Event Recall@10 is matched expected-major events in the first ten selected events divided by expected-major events. Top 3 Precision is matched expected Top-3-labelled events divided by the number actually selected in the up-to-three full-event set. Duplicate Story Rate is non-allowed excess selected events in a story family divided by selected events. Unsupported Claim Rate uses as denominator every validated claim-inventory record with script-owned `is_factual = true` and as numerator those records whose full deterministic/labelled support check is unsupported. Causal Overclaim Rate uses as denominator every inventory record with `is_causal = true` and as numerator those carrying a validated `causal_overclaim` finding. Inventory units and IDs—not sentences, clauses, punctuation, or arbitrary LLM fragments—define both denominators, and complete unique claim-audit coverage is required before scoring. Zero denominators are reported as `not_applicable` with `0/0`, never silently dropped; aggregates report summed numerators/denominators plus the count of applicable and non-applicable days.

Ranking Stability uses a fixed, versioned permutation list and recorded semantic outputs. Selected-event identity drift is set inequality over every selected full or compact event; selection-order drift is any difference in their complete stable ordered ID list, and the full-event subset and order are also reported. Every drift value must be zero for the deterministic correctness gate. Unsupported Claim Rate and Causal Overclaim Rate must also be zero for fixture-backed normal outputs. For the shipped v1 offline baseline, allowed Recall@10 and Top 3 Precision decrease is `0.000000`, and allowed Duplicate Story Rate increase is `0.000000`; changing or intentionally accepting a worse baseline requires an explicit versioned baseline/tolerance update rather than an automatic overwrite. These relative gates prevent silent regression but are not absolute proof of product quality. Credentialed repeated live evaluation remains an evidence report, not an automated release gate, because model output is non-deterministic.

### 19. Publication is immutable, monotonic, and serialized

Each validated run writes a create-only `feeds/daily/YYYY-MM-DD/<run_id>.json`, where the date is the cutoff date in `Asia/Shanghai`, before atomically replacing `feeds/latest.json`. The canonical `content_digest` covers the Feed after omitting both `content_digest` and `run_id`; `run_id` then derives from the fixed cutoff plus that digest, so neither value is circular. Validation recomputes both values from that same canonical projection. Repeating the same run ID and digest is an idempotent no-op; an existing path with incompatible content fails. The exclusive output-root collection lock remains held through cooperating publication. Every staging file/directory is an unpredictable sibling under its final parent and is verified on the same filesystem/device. Bytes are written create-only, flushed and file-`fsync`ed; the staging directory is `fsync`ed; dated artifacts commit with a platform atomic no-replace primitive; `latest` commits from a same-directory temp by atomic replace only after ownership validation; and each rename is followed by parent-directory `fsync`. The command fails startup capability validation if atomic no-replace, atomic replace, locking, or required `fsync` semantics are unavailable. A failure before a rename exposes no target artifact; a dated rename followed by parent-`fsync` failure returns typed `commit_durability_unknown`, leaves the create-only candidate untouched for validation/recovery, and does not attempt latest replacement. A latest replace followed by parent-`fsync` failure likewise returns `commit_durability_unknown`; it does not attempt rollback or claim which complete valid latest tuple will survive a later crash, but all immutable dated artifacts remain. Recovery/retry validates complete bytes and re-applies the maximum-tuple rule; missing, partial, or invalid state is a hard integrity failure. Latest ownership is the maximum lexicographic tuple `(evidence_cutoff_at, content_digest)`: a stale externally prepared candidate may preserve its dated artifact but cannot replace a newer latest, while equal-cutoff variants converge on the greater digest regardless of submission order and record the variant conflict. These defensive publication rules also validate recovery/import paths even though cooperating v1 CLI collections are serialized. Any failure before latest replacement leaves the previous valid latest untouched. Crash-recovery and every failure-injection point are tested.

GitHub Actions runs credential-free tests on ordinary hosted runners. The optional daily Feed workflow is restricted to a dedicated labelled self-hosted runner whose explicitly configured output root is a persistent volume shared by every scheduled/manual collection for those provider scopes. Startup validates a deployment-owned persistence marker plus readable/writable durable rate-state paths and fails before provider calls when that capability is absent. The checkout/output root is retained across jobs, and the workflow must disable destructive checkout cleanup for that root; an ephemeral hosted runner, fresh output root, or best-effort Actions cache cannot satisfy this persistence contract. The workflow uses a non-cancelling concurrency group in addition to the application lock, validates the generated Feed, stages the run-scoped dated file and latest file explicitly, commits them together, and uploads generated output even when publication fails. Branch-protection or commit failure fails the publication job; it is not reported as success. Creating or enabling a Git repository, remote, dedicated runner/volume, persistence marker, commit identity, branch policy, schedule, or write permission is a deployment action outside Apply.

### 20. Every Brief run produces a replayable local audit bundle

Every full or deterministic-degraded Brief attempt writes an atomic create-only local `runs/<brief_run_id>/` bundle containing a manifest, the exact canonical validated input Feed bytes as `input/feed.json`, a canonical fully resolved redacted non-secret effective-configuration snapshot, application-build/schema/config/prompt/model fingerprints, canonical events and ledger, verified packets, validated structured LLM outcomes, deterministic analytics and selection traces, Brief/degraded object with its claim inventory, rendered Markdown, audit findings, and an indexed `generation_status`. For a successful candidate this status is only `ready_for_commit`; it never preclaims renamed, durable, delivered, or terminal command success. A failed bundle may instead record the completed reversible stage and typed pre-commit failure. Commit/durability/delivery outcomes exist only in post-transaction external machine-readable command status/logging and never mutate the immutable bundle. The application build fingerprint is mandatory even without Git: SHA-256 over a closed, sorted path/size/file-SHA-256 manifest of `src/follow_the_money/`, thin runtime scripts, `pyproject.toml`, and `uv.lock`, plus the package version; an available Git SHA and dirty flag are only supplementary metadata. The terminal bundle manifest contains a closed, ordered member index with relative path, byte size, and SHA-256 for every other regular bundle file; unlisted files, duplicate/unsafe paths, and symlinks are rejected. The saved Feed's recomputed digest/run ID must equal the manifest input identity, the saved effective configuration must recompute its recorded fingerprint, and every evidence/ledger reference is rooted in that saved Feed. To prevent an ID/digest cycle, no indexed member may contain `brief_run_id` or `bundle_digest`; those values exist only in the terminal manifest, directory name, and post-commit external command status, while members cross-reference the independent attempt ID and Feed ID. `bundle_digest` hashes the canonical terminal-manifest projection with `bundle_digest` and `brief_run_id` omitted. `brief_run_id` then derives from the input Feed run ID, Brief generation instant, mode, application/config/prompt fingerprints, injected collision-resistant attempt ID, and bundle digest; validation recomputes the member index, manifest digest, and directory ID. The attempt ID allows same-clock and concurrent command retries to remain distinct, and an ID collision fails rather than overwriting. Secrets, authorization headers, raw hidden reasoning, and secret-valued configuration are never stored. Failed runs retain a redacted failure manifest and completed validated stages when storage remains available.

Normal daily execution never consumes prior bundles. `replay` accepts the explicit bundle alone, verifies member closure, exact saved Feed identity/producer provenance, saved effective-config fingerprint, current application-build and repository-schema fingerprints, then re-runs the full deterministic path from Feed validation through candidate graph, ledger, analytics, saved-output semantic merges, scoring, rendering, and audits without network or LLM calls. It injects the recorded `brief_generated_at`, `brief_completed_at`, attempt ID, and mode wherever historical freshness, watchlist, identity, or rendering requires them and never substitutes the current wall clock; offline replay does not re-enforce the original live monotonic deadline. Recorded prompts/model fingerprints remain provenance for the injected saved outputs and do not require current prompt/model access. Replay compares canonical Events, ledger, analytics, selected IDs/order, claim inventory, Brief/degraded object, rendered bytes, and audit results with their indexed saved counterparts; any drift or build/schema/Feed/config/member/manifest/digest/ID/cross-reference mismatch exits 1 before claiming a replay result. Inspecting an old manifest remains possible, but mismatched code cannot claim a replay.

All structured objects and rendered bytes remain in an unpredictable private staging sibling under the final `runs/` parent, with same-device verification. Every member is created without overwrite, flushed and file-`fsync`ed; the staging directory is `fsync`ed; then, while holding the run-root publication lock, a platform atomic no-replace directory rename creates the final bundle and the parent directory is `fsync`ed. Availability of the required lock/no-replace/fsync primitives is a startup capability check. A failure before rename exposes no final bundle or output bytes. If rename succeeds but parent `fsync` fails, the command returns typed `commit_durability_unknown`, leaves the create-only final-path candidate untouched, reports that candidate path on stderr, performs no convenience delivery, and does not claim durable publication or attempt rollback; later inspect/recovery must verify its full integrity closure before any use. Only rename plus successful parent `fsync` is the durable bundle publication point whose contained Markdown is authoritative. Only afterward may the CLI copy the already committed bytes to an explicit output path or stdout. A later convenience-delivery failure leaves the authoritative bundle intact and is reported distinctly rather than rolling it back or claiming it was never published.

### 21. CLI and external scheduling are explicit

Repository commands use versioned repo defaults plus explicit `--config` paths and never silently read machine-global state. A bundle-producing Brief attempt begins only after CLI parsing, configuration/output-root capability checks, input Feed validation, resolved-config redaction, and collision-resistant attempt-ID allocation succeed. Before that boundary, usage/configuration/credential/output-root/startup-capability rejection is typed `startup_rejection` and exits 2, while input Feed schema/digest/reference/domain/integrity rejection is typed `pre_attempt_domain_failure` and exits 1; neither promises a run bundle because no validated auditable input exists. After that boundary, runtime/LLM/audit/deadline failure must preserve an atomic redacted failed bundle when the validated run root remains writable; loss of that storage capability is reported on stderr and cannot be falsely recorded as a bundle. At attempt startup, one injected wall-clock `brief_generated_at` is captured as the immutable logical as-of time for freshness, watchlist selection, bundle identity, and rendered metadata; a separate `brief_completed_at` records completion. Normal or degraded processing fails with typed `clock_before_feed` before any LLM call if `brief_generated_at < evidence_cutoff_at` or `< feed.generated_at`, and publication also fails if the wall clock makes `brief_completed_at < brief_generated_at`; equality is allowed. Timeouts use the separate monotonic clock.

Every subcommand uses exit `0` only for complete requested success, `2` for CLI usage, configuration, missing required credential, or startup capability errors, and `1` for runtime/domain/schema/reference/integrity/tamper/capacity/deadline/publication/delivery failure. `feed --dry-run` performs no publication; a valid healthy or degraded Feed is success. `brief` succeeds only after a fully audited normal or explicitly requested degraded bundle is committed and requested convenience delivery succeeds; a delivery failure after commit reports the authoritative bundle path on stderr and never overwrites or deletes it. `replay` returns `1` for build/integrity/tamper mismatch. Offline `eval` returns `1` for invalid fixtures or failed gates; credentialed live evaluation returns `1` with machine-readable `incomplete` status when its request/time/cost budget prevents the declared repetitions from completing. Machine-readable status or committed artifact bytes go to the requested output file/stdout only after the applicable commit point, and diagnostics go to stderr.

The repository does not modify `~/.follow-the-money/config.json` or promise a local 08:30 invocation. V1 marks a Feed stale when `brief_generated_at - evidence_cutoff_at > 30 minutes` and refuses a normal Brief when that lag exceeds 2 hours. The 26-hour calendar snapshot therefore covers the complete `[brief_generated_at, brief_generated_at + 24h)` watchlist for every allowed normal run; any missing/shorter `calendar_horizon_end` fails the normal watchlist contract rather than claiming complete coverage. Deployment must explicitly reconcile any external delivery schedule with successful Feed publication and must not run the Brief before its input cutoff is available.

## Risks / Trade-offs

- [Free public endpoints change or throttle] -> Isolate adapters, use explicit user agents/timeouts, test contracts with fixtures, and surface per-source degraded warnings.
- [China official pages may lack stable machine-readable interfaces] -> Keep adapters small and optional, prefer official structured endpoints, and never replace missing official facts with guesses.
- [Title and snippet are insufficient for atomic extraction] -> Allow unresolved evidence and apply only in-Feed packet completeness checks rather than fetching after cutoff or inventing facts.
- [External evidence contains prompt injection or hostile payloads] -> Use allowlisted bounded HTTP clients, safe parsers, untrusted-data delimiters, no LLM tools, closed outputs, semantic cross-reference validation, and adversarial fixtures.
- [Daily observations cannot establish event causality] -> Label measurement resolution, keep price moves as observations, and constrain attribution to `direct`, `likely`, `concurrent`, or `unclear`.
- [Consensus and options data are unavailable without paid sources] -> Return unknown/unclear and do not reduce quality gates merely to produce a judgment.
- [A single LLM outage blocks full Brief generation] -> Preserve validated Feed and deterministic intermediate artifacts, and offer only an explicitly requested degraded deterministic report; do not add a hidden fallback.
- [Live model output varies despite low randomness] -> Canonicalize inputs, persist validated outputs and fingerprints, replay deterministic stages from saved outputs, and report repeated live evaluations without promising identical text.
- [Versioned heuristic scores bias events with missing data] -> Expose component coverage, use an explicit conservative missing policy and regression evidence, and never describe priority scores as returns or investment recommendations.
- [Workflow commits conflict with protected branches] -> Use narrow permissions and explicit publication failure; document artifact-only or pull-request deployment alternatives without silently changing default behavior.
- [Thirty real golden days require curation] -> Treat all 30 unique, provenance-reviewed days as an implementation completion gate and split curation into independently reviewable batches.
- [Schema and Python representations drift] -> Validate every serialized boundary with repository JSON Schemas and add schema compatibility tests.
- [Feed/bundle hashes provide internal integrity, not signer or producer-byte authenticity] -> Bind embedded producer descriptors, every bundle member, and directory ID into canonical digests, document the local trust boundary, and do not claim protection when an attacker can replace the artifact plus its external reference or when underlying producer files were not embedded.

## Migration Plan

1. Record the initial non-Change file inventory because the current OpenSpec root is not a Git checkout; Apply does not initialize Git, choose a license, commit, push, or enable workflows without separate authorization.
2. Build and test the repository against offline fixtures; no existing production data requires migration.
3. Run Feed generation in dry-run mode and inspect source health, fixed-cutoff behavior, freshness, and schema output.
4. Configure the single OpenAI credential/model and run an end-to-end golden fixture before scheduling Brief generation.
5. Reconcile the external delivery schedule so Brief execution occurs after Feed publication; do not silently consume or mutate the existing machine-global configuration.
6. Enable the GitHub daily workflow with write permission only after validating an initialized remote, commit identity, concurrency policy, and branch protection.
7. Roll back by disabling the daily workflow and reverting application files; immutable dated Feed artifacts and local run bundles remain audit evidence and require no database rollback.
